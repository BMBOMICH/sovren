A bug found while clearing up

check/all.sov had a check called "emu math" that loaded
/tmp/sov-emu.bin. Nothing ever wrote that file, so the check had been
failing quietly since the day it was added. It builds the binary

check/all.sov also never called tr_report, so the suite printed no
tally and always exited 0 — it could not fail. Both fixed.


Making the emulator general purpose
===================================

The first x86 emulator ran what Sovren emits. That is a much smaller
language than x86-64: about eighty opcodes out of several hundred,
and only the flag rules those eighty need.

What was added
--------------
  the eight sums in all six shapes, from a table rather than by hand
  adc and sbb, which no Sovren program uses but every C one does
  the shifts and rotates: shl shr sar rol ror rcl rcr, all three
    count forms, with the flag rules each leaves behind
  the full-width multiply and divide, where the answer is twice as
    wide as what went in and lives across rdx and rax
  the string instructions with rep and repne, both directions
  the bit instructions: bt bts btr btc, bsf bsr, bswap, popcnt
  cmpxchg and xadd, which locks are built from
  shld and shrd
  the parity, adjust and direction flags, and pushf and popf
  segment overrides, so fs and gs reach thread-local storage
  loop, loope, loopne, jrcxz, and the ret that drops stack with it
  the vector registers, and the whole-number instructions on them:
    movdqa movdqu movaps pxor por pand pandn pcmpeq pcmpgt pminub
    pmaxub pmovmskb pslldq psrldq punpck pshufd movd movq paddb
    and the rest of that family

Bugs this found
---------------
  Byte registers 4 to 7 are ah ch dh bh WITHOUT a rex prefix and
  spl bpl sil dil with one. Writing the wrong one is silent: the
  value lands in a register nobody is reading.

  x_bit returned minus one instead of one, because the remainder of
  a negative number is negative in Sovren.

  The vector registers overlapped each other. peek_i64 and poke_i64
  count in bytes, not in whole numbers, so a register sixteen bytes
  wide starts at n * 16, not n * 2.

  An address outside the block recorded a fault and then went ahead
  with the read anyway, which took the whole emulator down instead
  of stopping the guest.

  A thirty-two bit shift by nothing must still clear the top half of
  the register. Returning early skipped that.

  A thirty-two bit multiply built its answer with a signed divide,
  which rounds the wrong way once the product passes 2^63.

  Two thirty-two bit digits multiplied together reach almost 2^64,
  past what one Sovren number holds. The full-width multiply had to
  be done in sixteen bit digits instead.

  There were two handlers for the brk syscall, and the older one
  shadowed the newer.

  num_text, in the standard library and nothing to do with the
  emulator, returned a bare minus sign for the most negative number:
  negating it gives back itself, so the digit loop never ran.

How it was checked
------------------
  A differential checker fed the same random bytes to this and to a
  real processor, then compared all sixteen registers, every flag
  and a window of memory. 17,514 cases, no disagreements. Flags the
  Intel manual marks undefined are excluded, because real chips
  differ from each other there and comparing them proves nothing.

  check/x86ins.sov keeps 57 of those cases in the suite for good.

  A C program built by gcc and linked statically against the C
  library gives the same answer as it does natively. That exercises
  SSE, the string instructions, the full-width multiply and half the
  flag rules, because glibc is written that way.

What it still does not do
-------------------------
  Floating point arithmetic. A program that adds two decimals stops
  and says so rather than quietly giving a wrong answer.


Decimals
========

The last gap. A program that added two decimals stopped and said it
met an instruction it did not know.

Sovren has no decimal numbers, so this is all whole-number work. A
double is a sign, an eleven bit exponent and a fifty-two bit
fraction; the value is the fraction times two to the power of the
exponent. Adding two means lining up the exponents, adding the
fractions and rounding; multiplying means a hundred and six bit
product squeezed back into fifty-three; dividing and square root are
long division in binary, one bit of answer at a time.

Rounding is to nearest, and a tie goes to whichever way leaves the
last bit even. That is what makes the same sum give the same answer
twice, and it is why 0.1 + 0.2 is not 0.3 on any machine.

What was added
--------------
  add, take away, multiply, divide, square root, and the smaller and
    larger of two, at both widths, singly and in pairs
  comparing, both the kind that sets the ordinary flags and the kind
    that leaves a mask
  moving between whole numbers and decimals, both directions
  moving between the two decimal widths
  the very small numbers below the normal range, infinity, and
    not-a-number, which compares equal to nothing including itself
  two instructions from the old stack-based maths unit, because the
    C library reads its control word to find out how numbers round

Bugs this found
---------------
  Every instruction carrying a four-byte number read four bytes even
  when the 66 prefix said two. Everything after such an instruction
  then decoded as rubbish. A compiler rarely emits that prefix,
  which is why it went unnoticed until a C library turned up.

  F3 and F2 are the repeat prefixes, so they arrive as 1 and 2 — but
  F2 is the WIDE decimal one and F3 the narrow. They were the wrong
  way round, which made movsd and movdqu swap meanings: a load
  became a store and wrote sixteen bytes of text over a pointer.

  A scalar load has to clear the upper half of the register. Copying
  all sixteen bytes left rubbish there, and a loop adding up an
  array read it back.

  Twenty places called two jobs inside the arguments of a third.
  Those inner calls share scratch, so the first answer was quietly
  lost. This corrupted memory a long way from where it happened.

  x_d2i refused any number needing more than eleven places of shift,
  so anything over about two thousand came back wrong.

How it was checked
------------------
  Same method as before: a differential checker against the decimals
  this machine has. 5,400 operations across add, take away,
  multiply, divide, compare and square root, including infinity,
  not-a-number, the smallest number there is, and the largest.
  Every one bit-identical.

  check/x86ins.sov keeps 84 checks now, 27 of them decimals.

  Six C programs built by gcc, covering %f %e %g and %.17g, casts
  both ways, comparisons, square root and arithmetic on arrays, all
  print exactly what they print natively.


The old maths unit, and four new libraries
==========================================

x87
---
The last gap in the emulator. Before there were vector registers,
decimals were done on a stack of eight registers. A compiler only
reaches for it when a program asks for `long double`, but then it
does, so it is now there: the stack, the arithmetic, the compares,
the control word, and the ten byte number shape it stores.

Two bugs found while writing it:
  A loop that could never end, left in by mistake, which hung the
  whole emulator rather than failing.
  The ten byte shape carries a full sixty-four bit fraction, whose
  top bit is the sign bit of an ordinary Sovren number. Handing that
  straight to the rounding code made it loop forever.

Checked with a C program using `long double`: it prints exactly what
it prints natively. check/x86ins.sov now has 94 checks, 10 of them
for this.

win.sov — a real window
-----------------------
Speaks the X11 wire protocol straight down a socket. No toolkit, no
C library, no bindings. Opens a window, draws rectangles, boxes,
lines, circles and text, and reports keys and the mouse.

Three protocol bugs found, all of the same kind: a request whose
stated length did not match its real one. The server refuses those
silently, so the window appeared but nothing drew.
  CreateGC said five words when the two values made it six.
  GetInputFocus was sent as eight bytes with a window on the end; it
    is four bytes and takes nothing.
  PolyText8 needs a count byte AND a nudge byte before the letters.

ui.sov — buttons and boxes to type in
-------------------------------------
The tkinter-shaped one. Labels, buttons, boxes to type in, tick
boxes. ui_next deals with what the person did, redraws, and says
what happened.

game.sov — a game loop and things that move
-------------------------------------------
The pygame-shaped one. pygame is a Python library, but what it
gives you is a window, a loop at a steady speed, keys, and sprites,
and none of that is Python. The loop holds its pace to within one
per cent, which matters: without it anything that moves a step per
turn moves at a different speed on every machine.

web.sov, telegram.sov, discord.sov — bots
------------------------------------------
Both services refuse plain requests and insist on the locked kind,
which needs cryptography Sovren does not have. Rather than pretend,
these hand the locking to a helper the machine already has, and say
plainly when there is not one. Everything else is Sovren: building
the request, reading the reply, walking the JSON.

Both were checked twice: against a service run here, where every
part is exercised, and against the real Telegram and Discord, which
answered "Unauthorized" to a made-up token — which is the right
answer, and proves the request reached them.

env.sov — rewritten
-------------------
It read /proc/self/environ, which does not exist on Windows or a
Mac and is not readable at all in some places on Linux. env_get was
handing back nothing on machines where the setting was plainly
there. It now reads the settings off the stack, where the system
leaves them, which works everywhere. A new _sov_env_at in the
runtime does the reading.

Also found: str_cut takes an END, not a length. Several places in
the new libraries had it wrong, which silently truncated text.


The hang
========

A program using win.sov would sit there doing nothing, forever, if
the screen went away — the X server crashed, or was shut down, or
the connection was cut.

Two faults, one on top of the other.

First: win_flush asks the server a question and waits for the
answer. When the server is gone the answer never comes, so the wait
never ends. win_read_exact already returned early on a closed
socket, but nothing looked at what it returned, so the program
carried on and waited again next time round the loop.

Now the connection is marked dead the moment a read comes back
short or a write fails, and win_alive says so. win_wait hands back
WIN_CLOSE forever after that, game_running stops the game, and
ui_next returns UI_CLOSED. A loop that checks any of those now ends
by itself.

Second, and worse: writing to a socket whose other end has gone
kills the program on the spot, with no chance to notice or say
anything. That is the right default for a shell pipeline and quite
wrong for a program with a window. The exit code was 141, which is
the signal, and nothing was printed at all — so even the check that
was meant to catch this reported only "it stopped but did not say
why". sys_ignore_broken_pipe now asks for a plain error instead, so
the write fails, the code above sees it, and the program tidies up.

check/run now kills the screen out from under a running program and
insists it notices within ten seconds and says so. Without that
second fix the check failed; with it the program prints its message
and exits nought.


The hang, again — the real one
==============================

The first fix was for the window library: a program would wait
forever if the screen went away. That was real, and it is fixed.

It was not what was hanging.

edit.sov reads keys in a loop. key_read hands back minus one when
there are no more — the terminal was closed, or the input was a
file that has run out — and the loop did not look. So it went round
again, and again, reading nothing, forever, until it fell over.
Exit code 139, which is a crash, after sitting there doing nothing.

One line fixes it: stop when the key is below nought.

check/run now runs the editor with nothing on its input and insists
it exits by itself, and does the same for every example program.
Any of them that ever starts waiting for something that will never
come will now be caught here rather than by someone running it.


A window on Windows
===================

win.sov draws on Linux by speaking to the X server over a socket.
Windows has no X server; it draws through user32 and gdi32. Those
are genuinely different machines and there was no way round writing
both.

The obstacle was the import table. A Sovren Windows program carried
exactly eleven names from kernel32, at fixed places in head.bin.
Drawing needs about thirty-five more, from two further libraries,
and the table had no room and no way to hold a second library.

Rather than widen it to thirty-five, two names were added:
LoadLibraryA and GetProcAddress. Those two are the keys to
everything else — a program now opens any library on the machine
while it runs and finds anything inside it. Thirteen names in the
table, and the whole of Windows reachable.

Three things had to change together:
  head.bin, laid out again for thirteen: IAT at 0, ILT at 112,
    descriptor at 224, dll name at 264, names at 280, ending at 485
    of the 512 available.
  the PE writer, which had the old offsets written into it, and the
    data directory entry that points at the descriptor.
  cfunc, which was using the Linux way of handing over arguments.
    Windows puts the first four in rcx, rdx, r8 and r9 and wants
    thirty-two spare bytes above them. Calling a Windows library the
    Linux way puts every argument in the wrong place.

Then three libraries:
  winapi.sov   opening libraries and finding functions
  winwin.sov   a window, drawn with user32 and gdi32
  window.sov   picks whichever of the two works, so a program is
               written once and window_which says which it got

An emulator bug turned up doing this. Real Windows maps the file
headers at the load address as well as the sections; the emulator
only copied the sections. A program looking at its own import table
found nothing but zeroes.

Also: peek_raw8 takes an address AND an index, not one added
address. Passing one made every read come back nought.
